# NgRx SignalStore

A contest entry. State is held in NgRx SignalStore (`withState`, `withEntities`,
`withMethods`, `withComputed`, `rxMethod`), not in another approach's RxJS
classes. Loaders are the API services, which are Observables; the cache
around them is the store's own. Judged by the page tests
(`PAGE_TARGET=signal-store npm test`) and the e2e suite
(`E2E_CONTESTER=signal-store npm run e2e`).

Status: see [test_report.md](test_report.md), regenerated by `npm run test:report`.
The tool's gaps for this page are in [gaps.md](gaps.md).

## Idea

Every fetched entity (customer, orders, tiers, prices, ...) is one
`createKeyedCache` (`data/entity-store.ts`): a `signalStore` with

- `withEntities`: one slot per id, so every reader of the same id reads the
  same signal (R-L10);
- `attach(id)` / `detach(id)`: a reference count per id. The first attach
  starts the load; the last detach cancels a load still in flight and keeps a
  settled value;
- `reload(id)`, `set(id, value)`, `clear()`: Retry and polls, a write's
  result, and logout;
- `peek`, a `withComputed` read that is pure and safe inside `computed()`.

A view reads a key with `cacheEntry(cache, idSignal)`, which runs an
`effect()` that attaches the current id and detaches it in the cleanup. The
read itself is `peek`, because Angular forbids writing signals inside
`computed()`.

The customer list's filter, sort and page are a second, small store:
`UI_STATE` (`data/ui-state.ts`) holds named fields with `withState`,
`withMethods` and `patchState`. Its search text is typed into `typedText` at
once and debounced into `query.text` by an `rxMethod`.

Field components (`ProductName`, `CustomerTier`, `Kpi`, ...) each inject the
cache for their own value and take their own id as an input. No lookup comes
from a parent.

## Good

- A keyed read is one line in a field: `cacheEntry(this.cache, this.sku)`.
  The state (`loading`, `ready`, `reloading`, `error`) comes with it.
- One slot per id gives sharing for free: the list row, the header and the tab
  badge of one customer read the same tier entry (R-L10, R-J7).
- Typing is debounced by `rxMethod` in the customer list (R-L4), and the
  store's `withMethods` keeps each write next to the state it changes.
- Logout clears the user-bound caches in one call (`Auth.signOut`), and
  products, prices, stock and the product search are not in that list, so
  they survive it (R-L6, R-S4).

## Bad

Only failing requirements and the excess code they cost (spec §11). All three
are the tool's gaps G1 and G2, explained in [gaps.md](gaps.md).

- **Batching is not met** (R-L9; G2 in `gaps.md`). `tiers`, `ticketCounts` and
  `prices` go out one id per call: `A2`, `C11` (8 calls each for one list
  page), `C7`, `B10` (one `prices` call per hit), `C12` (24 `prices` calls for
  a 24-line cart, 2 expected), `D7` (one release shows only the first hit's
  price). The store has no batching primitive; meeting it means a per-tick
  buffer with chunks and per-id errors (vanilla's `entity-cache.ts`, 136
  lines) inside `createKeyedCache`.
- **The keyed async cache is hand-written** (R-L3, R-L5, R-L10, R-C4; G1 in
  `gaps.md`). `@ngrx/signals` holds state but does not load it.
  `createKeyedCache` and its readers (`entity-store.ts`, 132 lines) keep two
  `Map`s (observers and in-flight `Subject` per id) next to `withEntities`.
  The same job as vanilla's `Query`, but here every scenario it serves passes.
- **`untracked()` and the `peek`/`attach` split are a workaround.**
  `cacheEntry` wraps its attach and detach in `untracked()`: without it their
  signal reads become effect dependencies and a failed id retries forever.
  The split exists because `computed()` cannot write.

## Tradeoffs

Eight criteria, the same in every entry's README. Each is compared across the entries in [docs/contest/results](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/criteria.md); the numbers below come from there (line counts: card [06](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/06-boilerplate.md), Prettier-formatted, non-blank, non-comment).

- **Eager or lazy start.** Lazy. `cacheEntry` attaches its id from an `effect()`, which runs when the section that reads it is created (`data/entity-store.ts`). Gives: a hidden section asks nothing. Costs: the start goes through an `effect()` with `untracked()` attach/detach, kept right by hand.
- **One request per key, and how long a value lives.** `withEntities` gives one slot per id; an observer count per id decides when to start and when to stop. Values live until `clear()` on logout (`Auth.signOut`, `data/sources.ts` `SESSION_CACHES`). No eviction. Gives: one request per key. Costs: the count and the map of observers are written by hand.
- **Cancelling a superseded read.** The last `detach` cancels an in-flight load through a per-id `Subject` and `takeUntil` (`entity-store.ts`). Gives: a superseded answer is dropped. Costs: one more map of in-flight subjects to keep in step with the slots.
- **Batching.** None: each id is one call. Costs: the batch endpoints fail R-L9 (`gaps.md`); a batch would be new code on top of the store.
- **Keeping data on error or reload.** `reload()` sets `reloading` and keeps the value; a failed load sets `error` and keeps the last value (`fetched.error(value)`). Gives: the value is kept on purpose. Costs: every field needs its own error branch, `fieldError` in `data/block-state.ts`.
- **Boilerplate to add one value.** One more batched lookup like `tiers` costs 14 lines in 3 files (without batching, which is not met). The data layer is 618 lines: 259 generic, 157 per entity, 202 domain. Costs: a value must also be listed in `SESSION_CACHES` or logout keeps it.
- **Where state lives.** Values in root stores (`sources.ts`); UI state in one root store (`UI_STATE`). Gives: a value outlives the component that read it. Costs: root stores must be cleared on logout by hand (`Auth.signOut`).
- **Dependency on a library.** `@ngrx/signals`, plus RxJS for the loaders. Gives: the store's own primitives. Costs: the store API is the library's, so upgrades follow its changes.

## Try it

- Select different customers: the header, the tab badges and the list row all
  read the same tier entry; switch away and back and nothing refetches.
- Filter or sort the customer list: the query is held in `UI_STATE`, and a
  change to it reads a new key.
- Turn on **Throw** on any service in the request panel above the demo: the
  section fails in isolation, and its fields show an error with Reload.
- Open the Cart tab, leave the page and come back: the tab is remembered
  (R-S5); the customer and the open panel are not.
