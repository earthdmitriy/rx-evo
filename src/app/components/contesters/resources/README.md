# Signals + resource()

A contest entry built from Angular's primitives: `signal`, `computed`,
`linkedSignal`, `resource()` and `rxResource()`. No RxJS state classes of
another approach and no NgRx. Judged by the page tests
(`PAGE_TARGET=resources npm test`) and the e2e suite
(`E2E_CONTESTER=resources npm run e2e`). Written by an agent, like every
entry, and also steered by hand by the maintainer.

Status: see [test_report.md](test_report.md), regenerated by `npm run test:report`.
Failing scenarios and the tool's gaps are explained in [gaps.md](gaps.md).

## Idea

Components own their data. A section or field component reads a resource
from its own `rxResource()` or from a shared one. The shared ones come from
registries in `data/` (`*.registry.ts`): one per entity type (customers,
orders, order stats, ticket counts, products, prices, stock, carts, cart prices,
activity, the customer list, tiers). A registry creates one `rxResource` per key
on the first request and returns the same one afterwards; nothing loads until a
component asks. The registries are listed in `ResourcesSignedInComponent`'s
`providers`, so each lives in the signed-in frame's injector and is disposed
with it. Resources are bound to their registry and go with it.

A component reads a registry through a `computed`, with the registry call under
`untracked()` so that creating a resource does not happen inside the reactive
context. A view reads a resource's value only after `hasValue()`, because
`value()` throws in the error state. The block is `app-resource-block`, which
takes the resource itself.

Writes update the shared data and then bump a version in `Bus` (`data/bus.ts`,
root-provided counters for orders, order stats, stock and tickets). The
registries for those topics key their resources by `(id, version)`, so a bump
makes a new key and every reader shares the one new request.

UI state is plain signals in `data/ui-state.ts`. The editor's search text is
typed at once and debounced into a query with `toObservable` and `debounce`.

Where it fits: `resource()` is one async read owned by one component or
service. On a simple page, or an isolated part of one, where sections share no
data, loading, error, reload, cancel and disposal come with the owner, with no
extra code. It is not a cache. This page needs shared, cached and invalidated
data from stage 2 on, which is why the registries and the `Bus` exist, and
where most failures come from.

## Good

- A `resource()` with `params` cancels its superseded read and skips the loader
  for `undefined` params, so a section and its field need no code for either
  (R-C1, R-P5). That holds for component-owned resources; registry entries are
  the exception (see Bad).
- Sign-out needs no cache clearing: the frame and its registries are destroyed,
  and the components that read them with them (R-S3, R-S4).
- One registry per key gives one request per key for every reader in the
  session, including the activity list, the tier and the ticket counts
  (R-L3, R-L10, R-J7).

## Bad

Only failing requirements and the excess code they cost (spec §11). Each is
explained in [gaps.md](gaps.md), which also says where `resource()` fits: one
read per owner, not a shared cache.

Gaps of the tool (G1, G2 in `gaps.md`):

- **No shared cache, no invalidation** (R-C4, R-L5, R-L6). The registries keep
  resources as singletons outside their readers, so a kept entry is never
  cancelled: `B1` (a superseded customer read keeps running). An order
  registry broke B8 and was reverted: `C6` (a reopened order loads again).
  Root-scoped catalog registries broke the page harness and were reverted:
  `A7` (products and prices requested again after re-login).
- **No batching** (R-L9, R-J3, R-P3, R-P6): `A2`, `C11` (8 `tiers` and 8
  `ticketCounts` calls for one list), `C7`, `B10` (one `prices` call per hit),
  `C12` (26 `prices` calls for a 24-line cart, 3 expected), `D7` (one release
  shows only the first hit's price), `D9` (line prices and the cart total are
  separate calls; likely the same cause).

Implementation misses (not tried):

- **Version keys instead of reload** (R-C3, R-W10): `B3` (the Orders tab is
  `loading`, not `reloading`, after a save) and `C16` (stock asked for 3
  untouched skus). One `Bus` counter per entity makes a new, empty resource
  for every key. Calling `reload()` on the registry entries a write changed
  would keep the value and touch only those keys.
- **No value kept on a failed poll** (R-G4): `E7`. A failed `reload()` puts the
  resource in `error`, where `value()` throws, so the activity list goes.
  Keeping the last value next to the resource would fix it.
- **Notifications polled once in a minute** (R-L8): `C9` (1 request in 60 s, 2
  expected). Not traced.

Excess code, even where everything passes:

- **Registry plumbing:** twelve registries (289 lines, the same shape each) and
  the `untracked()` wrapper at each consumer, for R-L3, R-L10 and R-J7.
- **Version keys:** the `Bus` counters for R-W3 and R-W10; every reader of a
  write-affected key folds in the same version.
- **`hasValue()` guards:** every view reads a resource with `hasValue()` before
  `value()`, for R-E1. Without them a failed resource throws in its template.

## Tradeoffs

Eight criteria, the same in every entry's README. Each is compared across the entries in [docs/contest/results](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/criteria.md); the numbers below come from there (line counts: card [06](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/06-boilerplate.md), Prettier-formatted, non-blank, non-comment).

- **Eager or lazy start.** Lazy. An `rxResource` loads on its first read, and a registry creates a resource on its first `customer(id)` call (`data/*.registry.ts`). Gives: no request before a component reads. Costs: creation happens inside a read path, so every consumer wraps the registry call in `untracked()` (`customer-tier.component.ts`).
- **One request per key, and how long a value lives.** One resource per key in a registry's `Map`, alive for the signed-in frame (`resources-signed-in.component.ts`). No refcount, no eviction. Gives: one request per key. Costs: a superseded shared read keeps running (B1), and each write version leaves its old resource in the `Map` until logout.
- **Cancelling a superseded read.** Built in for component-owned resources: a changed `params` cancels the previous load. Not for registry entries (B1). Costs: two behaviours to know about, one per kind of resource.
- **Batching.** None, except the cart total, which is one resource over its skus (`cart-total.component.ts`). Costs: every batch endpoint needs its own shaping in the component.
- **Keeping data on error or reload.** A resource clears its value when it fails or its key changes, so stale data is not kept (E7, B3). Gives: no stale value can be shown by mistake. Costs: a failed poll blanks its list.
- **Boilerplate to add one value.** One more batched lookup like `tiers` costs 30 lines in 3 files (without batching, which is not met), most of it a new registry. The data layer is 773 lines: 31 generic, 320 per entity (the 12 registries), 422 domain. Costs: the registry file is the largest single piece of a shared value.
- **Where state lives.** Component-owned resources and the frame's providers. Root holds only the `Bus` version counters and `UiState`. Gives: a value's lifetime follows where it is provided. Costs: that lifetime is set in one provider list, not next to the read.
- **Dependency on a library.** Angular's `resource()` and `rxResource()` only. Gives: no third-party API. Costs: the behaviour is whatever Angular's resource implementation does, including `value()` throwing in the error state.

## Try it

- Select a customer, switch to another, and switch back: the first customer's
  profile, orders and activity come back from the session's registries without
  a request, and the first customer's reads keep running (B1).
- Open an order, edit items, search the catalog and add a hit: the hit and the
  new line briefly share a sku, then the search clears itself.
- Save an order: the Orders tab, the rail and the KPIs refresh because the
  version they read changed, not because their data was written directly.
- Turn on **Throw** for a service in the request panel: the section it feeds
  fails. Only a later poll or Retry brings its content back; nothing is kept
  meanwhile.
