## Idea

Every piece of data is a stateful observable from `@rx-evo/stateful-observable`.
A server entity addressed by an id (customer, cart, orders, notes, ...) is a
factory token (`statefulObservableFactory` in an `InjectionToken`, in
`sources/lookups.ts`). A factory gives one shared stream per id, so every reader
of an id reads the same entry: one request, one state. The three batch endpoints
(`tiers`, `ticketCounts`, `prices`) have batch factories
(`statefulObservableBatchFactory`), which collect the ids asked in one tick into
calls of at most 20.

State that is keyed by the UI (the customer list's query, the editor's search
text) is a stateful source owned by its component, with a cache key. Session
state is `sources/session.ts`: `login` and `logout` write streams, and
`loggedIn$` is derived from them. Every private source is `active: loggedIn$`.

A section binds independent streams and never joins them. Field components
(`ProductName`, `CustomerTier`, `Kpi`, ...) each project one entity's factory by
their own id input and render with `async`. Writes (`utils/action.ts`) are
streams whose input is a `Subject` of calls, with `exhaustMap`.

## Good

- Atomic sources: one source per entity; a counter has one owner and the KPI and
  the open-ticket badge of one customer share its stream (R-J1, R-J7).
- Latest wins by construction: `switchMap` in the stateful inputs, so a late
  answer of customer A cannot reach B (R-C1).
- Session hygiene with no teardown code: `active: loggedIn$` cancels in-flight
  reads and writes at logout and drops the caches (R-S3, R-S4, R-W5).
- Per-section status from the library: `pending$` is the block's `loading`,
  `error$` its `error`; a reload dims the shown data (R-B1, R-C3).
- Polls only while shown: the activity section reloads the entry it shows on a
  timer and stops with the section; the notifications poll is a `timer` in its
  section's loader (R-D2, R-L8).
- Writes with no double submit: `exhaustMap` plus `pending$` (R-W1, R-W2).

## Bad

Only failing requirements and the excess code they cost (spec §11). Nothing
fails in the current run (see `test_report.md`); [gaps.md](gaps.md) finds no
gap of the tool.

- **Excess code for R-G4 and R-C2:** the activity section keeps its list
  through a failed poll by passing the block no error while it shows a list of
  the shown customer. For that, the loader tags each list with its customer
  (one `map` in `ACTIVITY_BY_CUSTOMER`) and the template compares it, a few
  lines.

## Tradeoffs

Eight criteria, the same in every entry's README. Each is compared across the entries in [docs/contest/results](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/criteria.md); the numbers below come from there (line counts: card [06](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/06-boilerplate.md), Prettier-formatted, non-blank, non-comment).

- **Eager or lazy start.** Lazy. A stateful stream starts with its first subscriber, and `active` gates it on the session (`sources/lookups.ts`, `sources/session.ts`). Gives: a section that is not shown sends nothing. Costs: stream identity has to be understood to know when a request starts.
- **One request per key, and how long a value lives.** A factory gives one entry per key; the entry is released with its last subscriber, and `active: loggedIn$` drops every entry at logout. A settled value is kept after its last subscriber leaves, up to `cacheSize` (default 42; 200 or 500 where set). Gives: one request per key, with cleanup done by the library. Costs: the bound is per factory, set by hand where the default does not fit.
- **Cancelling a superseded read.** Built in: the library cancels a superseded read with the default factory. The six `refCount: false` lookups keep their read running on purpose, to keep the value. Gives: no code in the entry. Costs: the behaviour is the library's, not this entry's to change.
- **Batching.** Built in: `statefulObservableBatchFactory` collects the ids of one tick into calls of at most 20 (`sources/lookups.ts`). Gives: batching by configuration. Costs: the batch path is the library's, and nothing on it fails in the current run.
- **Keeping data on error or reload.** `pending$` and `error$` are per stream; a reload dims the shown data, and on a key switch the last value stays under the spinner (R-C2). The block shows the error or the content. Gives: stale content is shown dimmed, not blanked. Costs: a view that keeps its value through an error overrides the block's error itself (the activity section, with its customer tag).
- **Boilerplate to add one value.** One more batched lookup like `tiers` costs 13 lines in 2 files, the factory token being configuration. The data layer is 301 lines: 48 generic, 141 per entity (17 lookups), 112 domain. Costs: each field is its own `app-stateful-block` with `[stream]` and one `async` read of `value$`.
- **Where state lives.** Session and caches at root; the selected customer and open panel in components, passed down as inputs and up as events; the last tab in a root token (`LAST_TAB`). Gives: component state is local and explicit. Costs: the selection resets on navigation.
- **Dependency on a library.** `@rx-evo/stateful-observable`. Gives: the library's own cache policy. Costs: the entry was steered by the library's maintainer, so it is not an independent judge of the library; stated, not scored.

## Try it

1. Open `?seed=1&latency=slow`, sign in, select a customer, then quickly
   another: the main column dims under the spinner and then shows the new
   customer; the list rows fill in from their own requests.
2. Open the Cart of a customer with a long cart: each name arrives on its own, each
   price and line total in its own cell.
3. Open an order of a ticket, edit items, add a product, save and reply: the
   order, the cart row, the KPIs and the list badge refresh from the reloaded
   entries.
4. Log out while a slow request is pending, then log in again: nothing of the
   previous session shows, and the late answer is dropped.
5. Fail a source with the error toggles of the fake API: its section shows the
   error with Retry in place of the view; Retry asks only that source again.
