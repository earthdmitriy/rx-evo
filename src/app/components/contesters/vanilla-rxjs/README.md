# Vanilla RxJS

A contest entry: plain RxJS, as it ships with Angular. No data library, no
store, no `@rx-evo/stateful-observable`. Judged by the page tests
(`PAGE_TARGET=vanilla-rxjs npm test`) and the e2e suite
(`E2E_CONTESTER=vanilla-rxjs npm run e2e`).

Status: see [test_report.md](test_report.md), regenerated by `npm run test:report`.
The machinery built by hand: [gaps.md](gaps.md).

## Idea

The data layer is two caches and one store, all in `data/`:

- `query.ts`: a keyed read. One `Entry` per key, shared by every observer of
  it. The first observer starts the request; the last one to leave cancels a
  request still in flight; a settled value stays cached. Options: `pollMs`
  (refetch while observed) and `keepOnError` (keep the last data on failure).
- `entity-cache.ts`: a per-id read for the services that take ids. Ids asked
  in the same tick are collected, split into chunks of at most `MAX_BATCH`,
  and each id gets one slot. A failed batch turns only its own ids into
  `error`; a service without a batch endpoint gets one call per id.
- `sources.ts`: every query and cache of the console, and `clearSession()`,
  which forgets everything bound to the user. Products, prices, stock and the
  product search are public and survive logout.
- `console.store.ts`: the one injectable the console reads from. It holds one
  stream per section (`signedIn$`-gated), the writes with their
  invalidations, and the retry paths.
- `raw-models.ts`, `mappers.ts`, `vm.ts`: DTO to view model. Inside the store a
  row keeps the pieces other services enrich it with as `Fetched`, so "failed"
  and "not yet" stay distinct. `withParts` enriches a section once per new
  value. A failed enrichment is a notice on a ready section (`flag`), not a
  hidden field.
- `block-state.ts`, `fetched.ts`, `view-state.ts`: what a section's block gets
  (`loading`, `error`, `data`).

Field components read one stream per value from the store and take no lookup
input from their parents.

## Good

- Every behaviour is an operator at the place it belongs: `switchMap` for
  latest-wins and for logout (`signedIn$`), `debounceTime` for the search
  (R-L4), `finalize` for cancellation when the last observer leaves (R-C4),
  `combineLatest` only where a section needs more than one stream (R-P5).
- Nothing subscribes until a view asks (R-L2): streams are cold until
  observed, and a section that is not shown sends no request.
- A failure stays in its section: each section is its own stream, so one
  failing source does not block the rest (R-G3, R-P1).

## Bad

Only failing requirements and the excess code they cost (spec §11):

- **Caching, sharing and batching are hand-written.** `query.ts` (119 lines)
  and `entity-cache.ts` (136 lines) hold the bookkeeping for R-L3, R-L5, R-L9
  and R-L10: slots, observer counts, batch windows and stale flags. It is the
  largest single cost of the entry; [gaps.md](gaps.md) lists all the
  hand-built machinery, the baseline the other entries are compared with.
- **Retry is per source by hand.** `retryCustomerSource` switches over six
  keys and calls `retryIfFailed` or `retryFailed` for each, to meet R-G5 (only
  what failed is asked again).
- **Error notices are plumbing.** `failedCalls`, `flag` and `keepPrevious` in
  `vm.ts` carry the raw errors of enrichments and of stale data to the
  views, for R-E1, R-G2, R-G6 and R-C3.
- **Write guards are explicit.** `write()` checks `pending` for R-W2 and an
  `epoch` for R-W5 and R-W8 (a response from a previous session is dropped).

Nothing fails in the current run (102 page tests, 104 e2e). The B10 e2e failure of an earlier run ("execution context was destroyed") did not come back.

## Tradeoffs

Eight criteria, the same in every entry's README. Each is compared across the entries in [docs/contest/results](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/criteria.md); the numbers below come from there (line counts: card [06](https://github.com/earthdmitriy/rx-evo/blob/master/docs/contest/results/06-boilerplate.md), Prettier-formatted, non-blank, non-comment).

- **Eager or lazy start.** Lazy. An observable sends nothing until a view subscribes; the first observer of a `Query` key starts its request (`query.ts`, `attach`). Gives: a section that is not shown asks nothing. Costs: the rule "load when not loaded, stale or errored" is written here and must stay right.
- **One request per key, and how long a value lives.** One `Entry` per key in a `Query`, one slot per id in `EntityCache`. A settled value lives until `clearSession()` (`sources.ts`); there is no eviction. Gives: no duplicate request. Costs: memory grows for the whole session.
- **Cancelling a superseded read.** The last observer's `finalize` unsubscribes the in-flight request (`query.ts`, `detach`), and `switchMap` in the store takes the latest input. Gives: a late answer never reaches a newer view. Costs: the observer count is ours to keep right.
- **Batching.** Ids requested in one tick are collected and split at `MAX_BATCH` (`entity-cache.ts`). Gives: batch endpoints are called in batches. Costs: the per-tick collection and the mapping of a failed batch back to its ids are our code.
- **Keeping data on error or reload.** `keepOnError` keeps a polled value on failure; `stale` marks a key for refetch on the next observer; a failed enrichment is a notice on a ready section (`vm.ts`, `flag`). Gives: each case is explicit. Costs: three mechanisms for related behaviour.
- **Boilerplate to add one value.** One more batched lookup like `tiers` costs 20 lines in 4 files. The data layer is 1668 lines: 429 generic, 166 per entity, 1073 domain. Costs: the value crosses four layers before a view sees it, and the generic part is the hand-built cache and batching.
- **Where state lives.** One injectable, `console.store.ts`, owns every stream; components own none. Gives: one file shows the whole dataflow. Costs: that file is the largest in the entry and grows with each section.
- **Dependency on a library.** RxJS only, already shipped with Angular. Gives: no library to upgrade. Costs: all the caching above is ours.

## Try it

- Turn on **Throw** on any service in the request panel above the demo: the
  section fails in isolation, the rest of the page keeps working.
- Set **API speed** to Slow, then switch customers quickly: the latest
  selection wins, and the superseded read is cancelled.
- Open the Cart tab, leave the page and come back: the tab preference is
  remembered (R-S5); the customer and the open panel are not.
- Log out while a request is pending: nothing of the session stays on screen,
  and the late answer is dropped.
